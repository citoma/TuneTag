# TuneTag 项目整体 Review（2026-07-24）

> 范围：整体项目概览（README / PRD / 文档 / 设计 / Web 主应用 / 原生预研目录）
> 结论先行：产品定位清晰、Electron 主进程工程质量较高、安全基线正确；主要风险集中在**文档漂移（PRD 与实现不一致）**与**前端单文件巨石（App.tsx 1513 行）**，以及一处被低估的**“保存=导出到文件夹”语义与文档措辞不符**的问题。

---

## 1. 项目概况

| 维度 | 现状 |
|------|------|
| 产品 | 面向 macOS 的本地媒体标签批量编辑工具（乐签 TuneTag） |
| 主技术栈 | Electron 37 + React 19 + TypeScript 6 + Vite 8 |
| 核心依赖 | music-metadata（读）、node-id3（写 MP3）、ffmpeg/ffprobe（写非 MP3）、zustand（状态） |
| 代码规模 | 主进程 `main.mjs` 1505 行；前端 `App.tsx` 1513 行；其余较薄 |
| 仓库卫生 | 40 个文件被跟踪，无 `node_modules/dist/release` 泄漏，`.gitignore` 覆盖良好 |
| 测试 | 无（无 test 脚本、无测试文件） |

## 2. 亮点（值得保持）

1. **PRD 写作规范**：`docs/PRD_V1.md` 明确了 MVP 闭环、功能边界（Out of Scope）、状态模型与验收标准，是后续维护的良好锚点。
2. **Electron 安全基线正确**：`contextIsolation: true`、`nodeIntegration: false`，preload 通过 `contextBridge` 暴露受控 API，未直接暴露 Node 模块。
3. **主进程分层清晰**：`main.mjs` 内含约 50 个职责单一的函数（读/写/封面/冲突/Spotlight 同步按格式拆分），MP3 走 node-id3、其余走 ffmpeg，工程上合理。
4. **状态设计扎实**：zustand 中保留 `originals` 快照用于 `dirty` 计算，保存结果回写 `exportedPath` 与状态，逻辑闭环完整。
5. **打包脚本健壮**：`scripts/package-mac.mjs` 支持 arm64/x64、slim 变体、DMG 生成、electron-zip 缓存定位，比 README 里手敲 `npx @electron/packager` 更可靠。
6. **本地化细致**：排序用 `localeCompare('zh-CN', {numeric:true})`，UI 全中文，符合“面向中文场景”定位。

## 3. 问题与风险（按严重度）

### 🔴 High

**H1. PRD 与实现严重漂移（文档已不可信）**
- PRD §4 明确将 **封面编辑、歌词编辑**列为 V1 非目标；但 README“已实现能力”与 `App.tsx` 实际都支持这两项。
- PRD §3.4 规划了 **4 类批量操作**（设值/替换/清空/追加）；实现仅做到“设值 + 清空”，**缺失“批量替换（查找/替换）”与“批量追加（前缀/后缀）”**，且标题/艺术家有“留空不修改”的特殊规则。
- PRD §3.3 单文件字段为 6 个；实现扩展到 12 个（含曲作者/词作者/流派/自定义等）。
- 影响：贡献者无法以 PRD 为权威依据；验收标准与实际交付对不上。

**H2. 前端为单文件巨石 + 重复逻辑**
- `src/App.tsx` = 1513 行，包含 store 类型、工具函数、空状态、工作区、单文件编辑、批量编辑、预设弹窗、历史芯片——全部在一个组件内。
- `updateTrack` 与 `bulkUpdate` 中约 30 行的 `dirty` 计算块几乎逐字重复；`renderSingleEditor`/`renderBatchEditor` 对 10+ 字段重复“label+input+historyChips”结构。
- 影响：任何改动都需在巨型文件中定位，回归风险高，新人上手成本大。

**H3. “保存”语义与文档措辞不符（用户预期风险）**
- README/PRD 使用“保存写入”“写回文件”，暗示原地修改；但 `save-tracks` 实际是**弹出目录选择框、将文件导出（带新标签）到用户指定文件夹**，仅当目标文件夹恰为源文件夹并选“覆盖”时才原地改写。
- 这是更安全的“非破坏式导出”设计，方向合理，但**术语与行为不一致**会误导用户，需在 UI 与文档中明确为“导出/另存”。

### 🟠 Medium

**M1. 封面编辑仅 MP3 可用，文档未说明**
- `getEditableRules` 中 `coverEditable: ext === 'mp3'`，FLAC/M4A/WAV 的封面“更换/删除”按钮被禁用。README 笼统写“封面（APIC）支持替换与删除”，未标注格式限制。

**M2. 主进程单文件过大**
- `main.mjs` 1505 行虽内部分函数清晰，但仍建议拆分为 `meta/read`、`meta/write`、`cover`、`ipc`、`window` 等模块，便于测试与审阅。

**M3. 完全无自动化测试**
- 作为“会写文件的工具”，缺乏标签读写的 round-trip 单测、以及冲突策略（覆盖/保留/跳过）的覆盖，回归安全网缺失。

**M4. `TuneTagMac/` 是已废弃且分歧的原生预研**
- SwiftUI 原型含写死的示例数据、无真实导入/写标签能力；状态模型只有 3 态（缺 `clean/saving/saved`），与主线产品不一致。
- README 称其“早期原生尝试/预研目录”，但留在主仓库会诱导误操作/误解。建议删除或移入 `archive/` 并明确标注“非维护”。

### 🟡 Low / Minor

**L1. `sandbox: false` 未注明取舍**：主进程需 Node（webUtils/fs）故关闭沙箱属合理，但应在注释/文档中说明，便于后续评估能否回归。

**L2. `openExternalUrl` 建议校验 URL**：当前仅品牌链接以常量调用 `shell.openExternal`，风险低；但若将来接受外部传入，应限制协议白名单（仅 https）。

**L3. README 技术栈漏写 `zustand`**；`App.css` 仅 1 行（空文件，样式全在 `index.css`），属死文件。

**L4. 跨格式封面删除行为待验证**：`removeCover` 在 MP3（node-id3）路径生效；ffmpeg 写入路径是否真正清除封面需确认，避免“删封面”在部分格式下无效。

## 5. 总体评价

项目具备清晰的愿景与可用的 V1 闭环，Electron 侧工程质量高于平均水平。当前最需要投入的不是新功能，而是**“对齐”（文档与实现对齐、UI 与术语对齐）**与**“拆解”（前端巨石组件拆分）**两件事。完成 P0/P1 后，代码可维护性与用户信任度将有显著提升。
